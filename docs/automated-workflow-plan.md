# PR 流程自动化方案

> 状态：已确认方案，尚未实现
> 最后更新：2026-08-12

## 目标

将当前需要用户逐步点击的 PR 流程，升级为可配置、可暂停、可追溯的自动流程：

```text
新提交达到阈值
  → AI 检查/生成 PR 内容
  → 创建 PR
  → 等待 GitHub 门禁
  → 满足条件后按当前步骤策略合并
  → 等待合并后的 Checks、Actions、部署和健康检查
  → 满足下一步依赖后创建下一条 PR
```

自动化只负责执行用户明确开启的策略。GitHub 仍是分支保护、审批、Checks、Actions、Environment 和最终合并权限的权威来源。

## 用户需求理解

### 新提交触发

- 用户可以为流程设置新提交触发阈值，例如累计 1 个或 N 个新提交后再启动。
- 阈值只决定是否尝试启动，不绕过分支保护、重复 PR 检查或上游依赖。
- 同一个 Source → Target 在同一时刻最多保留一个自动创建中的 PR 任务。

### 每个步骤独立策略

每个流程步骤单独配置：

- 是否自动创建当前步骤 PR。
- 是否允许门禁通过后自动合并当前 PR。
- 是否在当前步骤完成后自动推进下一步。
- 是否必须人工审批。

### 自动创建 PR 的启用前置条件

“自动创建 PR”不是独立能力，必须依赖现有 AI 设置和生成规则。三个条件满足时，只代表该开关具备开启资格；系统绝不能替用户打开开关。只有用户主动点击步骤中的自动创建开关时，产品才立即校验：

1. AI 设置已开启“自动生成 PR 标题和描述”。
2. AI 设置已开启“自动确认创建 PR”。
3. 至少存在一条有效的 Markdown 生成规则；默认规则优先用于自动流程。

任一条件不满足时：

- 开关保持关闭，不保存不完整的自动化策略；满足条件时也必须等待用户主动点击。
- 显示明确原因，并提供打开 AI 设置或生成规则管理的入口。
- 不允许通过 API、旧配置或直接修改本地数据绕过同一校验。

自动流程实际创建 PR 时，复用现有创建 PR 的标题/描述生成、规则选择、草稿保存和创建 API；区别只在于满足前置条件后由后台自动确认，不再等待用户点击弹窗确认。生成内容和使用的规则必须写入自动化运行快照和审计记录。

步骤之间互不覆盖配置。多条 Source 路径汇聚到同一 Target 时，每条路径仍按自己的策略执行，下游汇聚步骤必须等待所有配置的前置路径完成。

### 合并后推进

当前 PR 合并后，自动流程必须继续等待：

- 合并后的 Checks/Commit Status。
- 合并后的 GitHub Actions。
- 配置的 Vercel/Cloudflare 部署。
- 配置的健康检查。
- 所有显式前置步骤的完成状态。

只有所有条件成功，下一步才会进入 `ready-to-create`；任何失败、超时、缺失配置或 GitHub 拒绝都会暂停自动流程。

### AI 失败处理

第一版只允许 AI 生成修复上下文、修复建议或 Codex 修复任务，不允许无人确认地修改代码、推送、创建修复 PR 或绕过门禁。

当前 AI API Key 只存在浏览器会话中，不能支撑关闭页面后的无人值守 AI。真正的后台 AI 自动修复需要单独设计服务端加密密钥、任务权限、成本限制和审计机制。

## 第一阶段设计：不使用画布

第一阶段直接扩展现有流程编辑器和流程详情，不引入画布。原因是当前流程已经支持线性步骤、独立路径和多路径汇聚；自动化的核心是策略和状态机，不是节点绘图。

### 编辑器体验

在现有步骤配置下增加“自动化策略”区域：

```text
feature/* → dev

[开关] 自动创建 PR       提交阈值：1
[开关] 门禁通过后自动合并
[开关] 合并后自动推进下一步
[开关] 需要人工审批
```

建议默认值：

- 自动创建 PR：关闭。
- 自动合并：关闭。
- 合并后自动推进：关闭。
- 人工审批：跟随 GitHub 分支保护；如果用户打开此开关，则产品额外要求人工确认。

即使用户打开自动创建 PR，若 AI 自动生成、自动确认或生成规则之后被关闭/删除，自动运行也必须暂停并提示配置已失效，不能继续创建 PR。

所有高风险策略默认关闭，用户必须逐步骤开启，避免已有流程升级后产生意外合并。

满足 AI 自动生成、自动确认和有效生成规则三项条件后，界面只解除开关的不可用状态，不改变开关的勾选状态。用户未点击前，不创建 PR、不生成后台任务，也不执行任何自动动作。

### 详情体验

步骤旁显示当前自动化状态：

```text
门禁已通过
自动合并：已开启
合并后推进：已开启
当前动作：等待合并后 Actions
```

用户可以在详情页暂停当前自动运行、查看阻塞原因、重试安全的失败动作或转到 GitHub 原生页面完成人工操作。暂停不会删除 PR 或运行记录。

## 服务端执行模型

浏览器只保存配置并发起控制请求，服务端负责调度和幂等：

1. Webhook 或 reconciliation 发现状态变化。
2. 服务端读取流程版本快照和步骤自动化策略。
3. 服务端复用统一阶段决策，确认当前动作确实为 `ready-to-create` 或 `ready-to-merge`。
4. 服务端写入自动化动作队列，使用稳定幂等键去重。
5. 执行 GitHub API 操作并记录请求、结果、操作者和失败原因。
6. 再次 reconciliation，确认 GitHub 实际状态后才推进下一个动作。

推荐状态：

```text
disabled
ready
queued
running
waiting-gates
paused
succeeded
failed
```

自动化动作不能仅凭一次 API 成功响应宣告流程完成，必须等 GitHub 状态投影确认。对于合并动作，GitHub 拒绝必须原样保留并暂停流程。

## 数据模型方向

后续新增迁移，不修改已执行迁移。建议增加：

- `workflow_automation_policies`：流程或步骤级策略。
- `workflow_automation_runs`：一次自动化运行的快照和生命周期。
- `workflow_automation_actions`：创建 PR、合并、等待门禁、推进等幂等动作。

策略快照必须写入运行记录。用户修改流程后，正在运行的自动任务继续使用原快照，新任务才使用新配置。

## 安全与保护

- 自动合并必须同时满足 GitHub 返回的 `mergeable=true`、`mergeable_state=clean`、审批和所有门禁条件。
- 生产合并和生产回滚仍保留独立权限和明确审计记录。
- 自动动作使用用户、流程版本、阶段 ID、Source、Target、提交 SHA 和动作类型组成幂等键。
- 每个步骤设置超时和最大重试次数；超过限制后进入 `paused` 并要求人工处理。
- 任何配置缺失、Actions 不存在、Environment 不存在或状态过期，都只能暂停，不能猜测成功。
- AI 修复不能直接获得 GitHub App secret、installation token 或长期 API Key。

## 实施顺序

1. 增加策略类型、默认值和编辑器配置，不执行自动动作。
2. 增加策略快照、自动化运行和动作表迁移。
3. 接入 `ready-to-create`，实现自动创建 PR 和阈值去重。
4. 接入 `ready-to-merge`，实现逐步骤自动合并和暂停/恢复。
5. 接入合并后门禁、部署、健康检查和多路径汇聚推进。
6. 增加运行详情、失败原因、审计和浏览器 E2E。
7. 在服务端加密 AI 配置和权限设计完成后，再评估后台 AI 修复。

## 画布决策

第一阶段不需要画布。现有步骤编辑器足以表达当前需求，成本低、迁移风险小、用户认知连续。

只有在需要任意 DAG、条件分支、并行节点、汇聚节点、回滚路径或人工审批节点可视化时，才引入画布。画布应作为配置的另一种视图，不能成为唯一编辑入口，也不能改变服务端统一状态模型。

## 验收标准

- 默认关闭自动化时，现有手动流程行为完全不变。
- 自动创建 PR 只有在 AI 自动生成、自动确认和生成规则三项均满足时才允许用户开启；缺少任一项时开关不可用且有可操作提示。满足条件不会自动勾选，必须由用户主动开启。
- 单步骤开启自动合并时，只有该步骤可自动合并。
- Checks、Actions、审批、mergeability 任一未满足时不会执行合并。
- 合并后的所有配置门禁未全绿时不会创建下一步 PR。
- 多路径汇聚必须等待全部显式前置路径完成。
- 重复 Webhook、重复轮询和重复点击不会创建重复 PR 或重复合并。
- 暂停、失败、重试、恢复和最终结果均可在详情与审计中追溯。
- 运行中的策略修改不会改变已创建运行的快照。
