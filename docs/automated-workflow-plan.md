# PR 流程自动化方案

> 状态：第一版本地已实现，但 2026-08-13 生产查询确认服务端自动创建 PR 实际未生效。本文保留原始设计假设；实际问题链、修复方案与回归清单见 [`auto-create-pr-remediation.md`](auto-create-pr-remediation.md)。
> 最后更新：2026-08-15

## 目标

将当前需要用户逐步点击的 PR 流程，升级为可配置、可暂停、可追溯的自动流程：

```text
新提交达到阈值
  → AI 检查/生成 PR 内容
  → 创建 PR
  → 等待 GitHub 门禁
  → 满足条件后按当前步骤策略合并
  → 等待合并后的 Checks、Actions、部署和健康检查
  → 满足下一步依赖后创建下一条 PR
```

自动化只负责执行用户明确开启的策略。GitHub 仍是分支保护、审批、Checks、Actions、Environment 和最终合并权限的权威来源。

## 第一版实现状态

- `024`–`031` 已由用户在 Supabase 执行；Vercel Production 和 Preview 已配置 `AI_CREDENTIALS_ENCRYPTION_KEY`。
- 用户主动开启某一步“自动创建 PR”时，前端会把当时的默认 Markdown 规则名称、正文和捕获时间写入该步骤策略快照。后续默认规则改变不会静默改变已启用步骤的自动化行为。
- Webhook、Cron 和 inbox reconciliation 在阶段统一决策进入 `ready-to-create` 时，服务端基于 `workflow + stage + source + target + head SHA` 生成稳定幂等键，入队并原子领取执行；关闭页面不影响执行。
- 执行前再次验证当前决策、服务端加密凭据、自动生成、自动确认、规则快照、Source 新提交和无同路径开放 PR。失败动作暂停并保留原因；AI 失败时不使用未经确认的兜底文案创建 PR。
- 历史 `browser-session` 策略保持兼容但不会被后台执行；用户需关闭后重新主动开启，才会保存服务端规则快照。
- 仍明确不做自动合并、Production 自动合并、自动代码修改或自动回滚。

## 用户需求理解

### 新提交触发

- 用户可以为每个流程步骤设置新提交触发阈值，默认 1；累计达到 N 个新提交（`aheadBy >= N`）后才启动自动创建 PR。
- 阈值已落地到步骤自动化策略，仅在流程详情页的步骤控制区修改；流程编辑页不显示自动创建配置。旧策略未保存阈值时按 1 兼容。
- 阈值只决定是否尝试启动，不绕过分支保护、重复 PR 检查或上游依赖。
- 同一个 Source → Target 在同一时刻最多保留一个自动创建中的 PR 任务。

### 每个步骤独立策略

每个流程步骤单独配置：

- 是否自动创建当前步骤 PR。
- 是否允许门禁通过后自动合并当前 PR。
- 是否在当前步骤完成后自动推进下一步。
- 是否必须人工审批。

### 自动创建 PR 的启用前置条件

“自动创建 PR”不是独立能力，必须依赖现有 AI 设置和生成规则。三个条件满足时，只代表该开关具备开启资格；系统绝不能替用户打开开关。只有用户主动点击步骤中的自动创建开关时，产品才立即校验：

1. AI 设置已开启“自动生成 PR 标题和描述”。
2. AI 设置已开启“自动确认创建 PR”。
3. 至少存在一条有效的 Markdown 生成规则；默认规则优先用于自动流程。

任一条件不满足时：

- 开关保持关闭，不保存不完整的自动化策略；满足条件时也必须等待用户主动点击。
- 显示明确原因，并提供打开 AI 设置或生成规则管理的入口。
- 不允许通过 API、旧配置或直接修改本地数据绕过同一校验。

自动流程实际创建 PR 时，复用现有创建 PR 的标题/描述生成和创建 API；区别只在于满足前置条件后由后台自动确认，不再等待用户点击弹窗确认。生成规则正文只写入受访问控制的自动化运行/动作快照，不写入操作审计、错误、通知或遥测；审计仅记录动作类型、流程、阶段和 PR 编号。

步骤之间互不覆盖配置。多条 Source 路径汇聚到同一 Target 时，每条路径仍按自己的策略执行，下游汇聚步骤必须等待所有配置的前置路径完成。

### 合并后推进

当前 PR 合并后，自动流程必须继续等待：

- 合并后的 Checks/Commit Status。
- 合并后的 GitHub Actions。
- 配置的 Vercel/Cloudflare 部署。
- 配置的健康检查。
- 所有显式前置步骤的完成状态。

只有所有条件成功，下一步才会进入 `ready-to-create`；任何失败、超时、缺失配置或 GitHub 拒绝都会暂停自动流程。

### AI 失败处理

AI 生成标题或描述失败时，自动动作进入 `paused`，保存脱敏失败原因，不继续创建 PR，也不自动替换为兜底标题/描述。用户可以接管当前动作：重新生成，或手动填写标题和描述；用户确认内容后点击“继续自动流程”（Unpause），系统复用原动作的幂等身份继续执行。取消或未确认时流程保持暂停。任何手动兜底文案都必须经过用户明确确认，不得由无人值守流程自动采用。

自动动作的失败、暂停、接管和恢复必须在流程详情与审计记录中可追溯；恢复前再次检查 Source、Target、开放 PR、门禁和动作幂等状态，避免重复创建。

当前 AI API Key 保存在浏览器 `sessionStorage`。同一标签页刷新和站内跳转后仍然存在，但 Vercel 后端、GitHub Webhook 和定时 reconciliation 无法读取；关闭标签页、换浏览器或换设备后也不能作为可靠凭据。因此它可以继续支撑手动创建 PR，但不能支撑关闭页面后的无人值守 AI。

## AI Key 存储方案

AI Key 分成两个相互独立的使用层级，不迁移或删除现有浏览器配置：

1. **浏览器会话 Key（现状）**：继续保存在 `sessionStorage`，用于手动创建 PR 和用户在页面内主动触发 AI。它在同一标签页刷新后保留，不上传服务端。
2. **自动流程 Key（后续）**：只有用户明确启用无人值守自动流程并单独保存后，才由服务端加密保存，供 Webhook、reconciliation 和动作队列使用。

自动流程 Key 的正式方案：

- 浏览器通过受认证、受 CSRF 和限流保护的 API 提交明文；响应完成后前端不再保存该明文副本。
- Vercel 后端使用 AES-256-GCM 加密，数据密钥版本由 `key_id` 标识；主密钥只存在 Vercel 环境变量，不进入数据库、日志或浏览器包。
- Supabase 只保存密文、IV、认证标签、提供商/Base URL、模型、掩码、密钥版本、创建时间、更新时间和最后使用时间。
- API 只允许创建、替换、测试和删除凭据；读取接口只能返回掩码与状态，绝不返回明文。
- 自动化运行只在执行 AI 请求的短时间内解密；错误、审计和遥测必须过滤 Authorization Header、API Key 和生成规则中的敏感内容。
- 支持主密钥轮换、用户凭据替换和删除；删除或解密失败时，相关自动流程进入 `paused`，不得退回浏览器 Key 或继续猜测执行。
- 团队共享流程第一版不共享个人 AI Key。正式开放前必须单独确定凭据所有者、使用额度、成员权限和离队后的处理规则。

现有“加密云同步”不能直接复用为后台凭据存储：它由用户口令在浏览器派生密钥，服务端只能保存密文，无法在无人值守任务中解密。这一边界必须保留。

### 第一版可行性验证

第一版只验证服务端加密凭据能否安全支撑一次受控的自动 PR 内容生成，不同时实现完整自动流程：

1. 新增独立的服务端 AI 凭据保存、状态、测试和删除 API，以及 `024_ai_automation_credentials.sql`；不修改已执行迁移。部署前必须配置 `AI_CREDENTIALS_ENCRYPTION_KEY`（32 字节 hex 或 base64）。
2. AI 设置中增加“用于自动流程”的独立配置入口和清晰状态；必须由用户主动保存，不因现有浏览器 Key 存在而自动上传。
3. 用测试仓库和非生产步骤执行一次受控验证：服务端读取默认 Markdown 规则，生成 PR 标题和描述，但在 PoC 验收前仍停在确认边界，不自动合并。
4. 验证数据库、API 响应、Vercel 日志和操作审计中均不存在明文 Key，并验证替换、删除、解密失败和主密钥版本不匹配时会安全暂停。
5. PoC 通过后再接入步骤级“自动创建 PR”开关；满足所有前置条件只解除开关禁用状态，仍必须由用户主动开启。

第一版不复用页面弹窗作为后台运行载体，也不以“页面必须保持打开”冒充无人值守能力。现有手动创建 PR 链路和浏览器 Key 行为保持不变。

服务端凭据保存接口只允许公网 HTTPS Base URL，并拒绝 localhost、常见 RFC1918 地址和 `.local` 主机名，避免保存前的连通性测试形成明显 SSRF 入口；正式上线前仍需结合出站网络策略和 DNS 解析策略复核。

## 第一阶段设计：不使用画布

第一阶段直接扩展现有流程编辑器和流程详情，不引入画布。原因是当前流程已经支持线性步骤、独立路径和多路径汇聚；自动化的核心是策略和状态机，不是节点绘图。

### 编辑器体验

在现有步骤配置下增加“自动化策略”区域：

```text
feature/* → dev

[开关] 自动创建 PR       提交阈值：1
[开关] 门禁通过后自动合并
[开关] 合并后自动推进下一步
[开关] 需要人工审批
```

建议默认值：

- 自动创建 PR：关闭。
- 自动合并：关闭。
- 合并后自动推进：关闭。
- 人工审批：跟随 GitHub 分支保护；如果用户打开此开关，则产品额外要求人工确认。

即使用户打开自动创建 PR，若服务端自动流程凭据被删除/失效，或 AI 自动生成、自动确认、生成规则之后被关闭/删除，自动运行也必须暂停并提示配置已失效，不能继续创建 PR。

所有高风险策略默认关闭，用户必须逐步骤开启，避免已有流程升级后产生意外合并。

满足服务端自动流程凭据、AI 自动生成、自动确认和有效生成规则四项条件后，界面只解除开关的不可用状态，不改变开关的勾选状态。用户未点击前，不创建 PR、不生成后台任务，也不执行任何自动动作。

### 详情体验

步骤旁显示当前自动化状态：

```text
门禁已通过
自动合并：已开启
合并后推进：已开启
当前动作：等待合并后 Actions
```

用户可以在详情页暂停当前自动运行、查看阻塞原因、重试安全的失败动作或转到 GitHub 原生页面完成人工操作。暂停不会删除 PR 或运行记录。

### 自动合并进度条

> 2026-08-15：本节方案保留，但实施已由用户明确后置，先解决自动创建 PR / 自动合并 PR 本身的稳定性。排序与前置条件见 [`docs/current-state.md`](current-state.md) 的「下一阶段优先级」第 5 项。

流程详情页增加与步骤列表一致的自动化进度条，按流程顺序展示每个阶段的状态。进度条不是装饰性百分比，而是当前统一状态模型的可视投影：

- 已完成步骤：门禁、合并后 Checks/Actions、部署和健康检查均成功，显示完成标记；
- 当前步骤：显示正在执行的动作，例如“生成 PR 内容”“等待审批”“等待合并后 Actions”“等待 Preview 部署”或“用户接管”；
- 下一步：显示满足当前步骤后将进入的步骤及其依赖，未解锁时保持待处理；
- 上一步：允许查看已完成或失败的上游步骤，但不能绕过门禁直接推进；
- 暂停/失败：进度条在对应步骤停住，显示原因、最近更新时间和可执行操作（重试、重新生成、手动填写、Unpause 或前往 GitHub）；
- 多路径汇聚：只有所有前置 Source → Target 路径完成后，汇聚步骤才显示为可执行；
- 自动合并关闭时，当前步骤仍展示真实 GitHub 状态，但不显示“自动合并中”，避免把人工合并误认为后台动作。

进度条的当前、上一步和下一步必须由服务端阶段决策与动作队列共同计算，不能仅按浏览器最后一次刷新结果推断。用户在 AI 失败后接管并确认内容时，进度条从“已暂停”切换为“等待恢复/执行中”，恢复仍沿用原动作的幂等身份。

### AI 失败节点的交互规格

进度条放置在每个步骤的“自动创建 PR”控制区下方；每个流程步骤对应一个节点。节点不代表单独的 GitHub 操作，而是该步骤自动运行状态的摘要。

| 状态 | 节点表现 | Hover Tooltip | 点击行为 |
| --- | --- | --- | --- |
| `succeeded` | 绿色勾选 | 步骤、Source → Target、完成时间、门禁摘要 | 打开只读运行详情 |
| `running` / `queued` | 深色高亮或呼吸点 | 当前动作、开始时间、最近更新时间 | 打开状态抽屉，可刷新，不允许重复执行 |
| `paused`（AI 生成失败） | 黄色暂停标记 | “AI 生成失败”、脱敏原因、暂停时间 | 打开“接管 AI 内容”弹窗 |
| `failed` | 红色警示 | 失败动作、失败原因、重试次数 | 打开失败详情和安全重试操作 |
| `waiting-gates` | 黄色等待标记 | 等待的 Checks、Actions、Approval、部署或健康检查 | 打开门禁明细，不绕过 GitHub 门禁 |
| `locked` / `ready` | 灰色或浅色 | 上一步/前置路径及解锁条件 | 打开阻塞步骤详情 |

“接管 AI 内容”弹窗必须包含：

- Source → Target、提交数量、生成规则名称和当前动作编号；
- PR 标题输入框、PR 描述编辑器；
- “重新生成”按钮，沿用当前服务端凭据和规则快照；
- “确认并继续自动流程”按钮；
- “取消”按钮，取消只关闭弹窗，节点继续保持 `paused`。

用户重新生成成功或手动填写有效标题/描述后，点击“确认并继续自动流程”：

1. 前端提交标题、描述和原动作 ID；服务端校验用户权限、动作仍为 `paused`、Source/Target/提交 SHA、规则快照和无同路径开放 PR；
2. 服务端保存用户确认的 PR 内容，动作原子地从 `paused` 恢复为 `queued`，保留原幂等身份；
3. 执行器继续创建 PR。创建成功前，节点只显示“内容已确认，等待创建 PR”，不能直接变绿；
4. GitHub PR 创建成功并完成状态投影后，该步骤节点才变为绿色；下一步骤只有在当前 PR 的 Checks、审批、合并后 Checks/Actions、部署和健康检查全部满足后才激活。

节点变绿表示整个步骤已通过，不表示仅 AI 标题/描述确认成功。任何过期动作、内容为空、Source/Target 变化或已存在开放 PR 都必须拒绝恢复并继续保持暂停。

## 服务端执行模型

浏览器只保存配置并发起控制请求，服务端负责调度和幂等：

1. Webhook 或 reconciliation 发现状态变化。
2. 服务端读取流程版本快照和步骤自动化策略。
3. 服务端复用统一阶段决策，确认当前动作确实为 `ready-to-create` 或 `ready-to-merge`。
4. 服务端写入自动化动作队列，使用稳定幂等键去重。
5. 执行 GitHub API 操作并记录请求、结果、操作者和失败原因。
6. 再次 reconciliation，确认 GitHub 实际状态后才推进下一个动作。

推荐状态：

```text
disabled
ready
queued
running
waiting-gates
paused
succeeded
failed
```

自动化动作不能仅凭一次 API 成功响应宣告流程完成，必须等 GitHub 状态投影确认。对于合并动作，GitHub 拒绝必须原样保留并暂停流程。

## 数据模型方向

后续新增迁移，不修改已执行迁移。建议增加：

- `workflow_automation_policies`：流程或步骤级策略。
- `workflow_automation_runs`：一次自动化运行的快照和生命周期。
- `workflow_automation_actions`：创建 PR、合并、等待门禁、推进等幂等动作。

策略快照必须写入运行记录。用户修改流程后，正在运行的自动任务继续使用原快照，新任务才使用新配置。

## 安全与保护

- 自动合并必须同时满足 GitHub 返回的 `mergeable=true`、`mergeable_state=clean`、审批和所有门禁条件。
- 生产合并和生产回滚仍保留独立权限和明确审计记录。
- 自动动作使用用户、流程版本、阶段 ID、Source、Target、提交 SHA 和动作类型组成幂等键。
- 每个步骤设置超时和最大重试次数；超过限制后进入 `paused` 并要求人工处理。例外是「等门禁」这一类：它按设计留在 `queued` 以便被清门禁的事件接上，因此由时间退避而不是尝试次数封顶，见《重试上限》。
- 任何配置缺失、Actions 不存在、Environment 不存在或状态过期，都只能暂停，不能猜测成功。
- AI 修复不能直接获得 GitHub App secret、installation token 或长期 API Key。

## 第 5 阶段：逐步骤自动合并设计

2026-08-14 与用户确认。自动合并与自动创建是两个**独立**的按步骤开关：自动创建建错了可以关掉 PR，自动合并是对目标分支的不可逆写入，不能共用一个勾选。开关随 `automation` 挂在每个步骤上（见 `src/lib/workflow.ts` 的 `WorkflowStage`），因此指向 `main` 的那一段由它自己的开关决定，不设全局开关，也不额外加二次确认弹窗——授权体现为用户主动逐步骤勾选，加上本设计条目在文档中留痕。生产合并仍要独立审计标记；自动回滚依旧不做。

### 合并方法

只实现 merge commit。手动路径当前也只开放这一种（`src/main.ts` 硬编码 `mergePullRequestPayload('merge', pull.head.sha)`），自动路径保持一致，避免两条路径行为不一致。类型上保留 `'merge' | 'squash' | 'rebase'` 以便后续迭代放开，但本阶段配置层写死 `merge`。

合并请求必须带 `sha = pull.head.sha`：head 一旦前进，GitHub 会拒绝这次合并，这是防止「门禁绿的是旧 commit、合并的是新 commit」的关键保护，不可省略。

### 门禁判定

沿用《安全与保护》：只有 GitHub 返回 `mergeable = true`、`mergeable_state = 'clean'`、审批与所有必需门禁均满足时才执行合并。判定必须在执行前重新向 GitHub 取，不使用库里的缓存状态。

**必需审批数要同时读两个来源。** GitHub 的经典分支保护与 ruleset 是并行生效、由不同端点上报的：一个分支若把审批要求只写在 ruleset 里，`/repos/{o}/{r}/branches/{b}/protection` 会完全不返回 review 段，于是投影里的 `required_approvals` 是 0，判定跳过审批那一支、落到笼统的 `blocked`。`requiredApprovalsFromProtection(protection, rules)` 并行取 `/rules/branches/{b}` 并取两者较严者（已合并的 PR 跳过这次调用）。

`mergeable_state = 'behind'`（仓库开启「Require branches to be up to date」且 base 已前进）**只暂停，不自动 update branch**。理由：update branch 是对源分支的写入，会触发新一轮 CI，并使 head sha、幂等键和待用 `sha` 同时失效，还可能与自动创建互相触发形成循环。暂停后由用户在 GitHub 或详情页处理。

### 重试上限

现有机制是失败动作落 `paused`，超过 120 秒被 `enqueueServerAutoCreate` 的 stale 逻辑重置回 `queued`。这对自动创建是自愈能力（`P9` 即靠它恢复），但对合并有害：冲突、缺审批、必需检查为红都属于**人工才能解决**的失败，无上限重排会每轮重试、每轮写一条失败原因和审计，刷满队列、白耗 API 配额，并让界面看起来「系统在努力」而实际永不成功。

因此 `merge-pr` 必须有重试上限：复用工作流上已有的 `recoveryPolicy { maxRetries, cooldownSeconds }`，超过 `maxRetries` 后停在 `paused` 且不再自动重排，必须人工恢复。这也落实《安全与保护》中「每个步骤设置超时和最大重试次数」。

**2026-08-15 修正：上面这个上限漏掉了一整类路径。** `automationRetryIsExhausted` 只读走到过判决的行，而「门禁未全绿」「审批不足」「mergeability 未判定」这几种原因被标为 `retryable`，执行器按设计把动作留在 `queued`（不是 `paused`）以便被清门禁的事件接上——`queued` 不在上限的视野里，所以这条路径**根本没有上限**。迁移 `030` 把排空收到每 2 分钟后代价才显形：一个只差一个 Approval 的 PR 在 74 分钟里累计 46 次尝试，每次都花 GitHub 调用，而门禁只有人能清。本节原本担心的浪费确实发生了，只是走的是另一条路。

修法的前提是**定时重试不是时效来源**：清门禁的事件本身会触发校准，而 `scheduleServerAutoMerge` 命中已 `queued` 的行会就地执行，所以排空的重试只是「事件漏了」的兜底。于是 `automationGateWaitDelayMs(attempts, policy)` 让带 `failure_reason` 的 `queued` 行等一段时间才重跑：等待时长取同一个 `recoveryPolicy.cooldownSeconds`（默认 300 秒，可配 0–86400，显式配 0 表示不等），随尝试次数翻倍，封顶 `AUTOMATION_GATE_WAIT_MAX_MS = 30 分钟`——封顶存在的理由是漏掉的事件要在同一小时内被兜回来。`automationDrainDecision` 因此多了第三个可选参数 `policy?: { cooldownSeconds?: number }`，排空查询多取 `workflows.payload->'recoveryPolicy'->>'cooldownSeconds'`。注意该列缺省时必须传 `undefined` 而不是 `Number(null)`——后者是 0，会把没配策略的流程全都读成「不等待」。

### 幂等

执行前先读 PR 状态：已经是 merged 就直接记 `succeeded` 并带上 PR 号，不调合并接口、不报错。与自动创建的「已有开放 PR 记幂等成功」分支对称，覆盖重复 Webhook、重复轮询以及用户在入队后手动抢先合并这三种情况，避免产生一批「其实目标已达成」的失败记录。

幂等键沿用 `用户 + 流程版本 + 阶段 ID + Source + Target + 提交 SHA + 动作类型`，动作类型为 `merge-pr`。

### 两个开关不强关联（状态独立），但勾选资格对齐

自动合并的策略**不依赖**自动创建的策略：两者各自独立勾选，开关任一方不会清除另一方，一个步骤可以只开自动合并。理由：

- **前置条件不同**。自动创建要求服务端自动流程凭据、AI 自动生成、自动确认和有效生成规则四项；自动合并完全不使用 AI。强关联等于把 AI 的前置条件强加到一个不需要 AI 的功能上。
- **两种用法都真实存在**。PR 描述由人写、门禁绿后自动合并；以及 AI 写描述、合并由人确认。强关联会把两类用户都堵成全有或全无。
- **避免隐式联动**。若自动合并依赖自动创建，用户关闭自动创建时会静默停掉自动合并。对合并这种不可逆动作，「关掉 A 顺带关掉 B」是事故来源。

技术上也不需要关联：合并动作由步骤进入 `ready-to-merge` 触发，该状态与 PR 由谁创建无关，人工创建的 PR 同样会进入。

因此界面文案必须写明：自动合并作用于该步骤路由上当前存在的 PR，不区分由 AI 还是人工创建。

**勾选资格例外（2026-08-14 用户决定）**：界面上自动合并的可勾选条件与自动创建**对齐**，即同样要求服务端自动流程凭据、AI 自动生成标题描述、自动确认创建和至少一条有效生成规则，另外还要求 `pull-merge` 权限；四项前置缺失时两个勾选框一起禁用。这是产品一致性取舍，代价是「只想自动合并、不想自动创建」的用户也必须先配好 AI 凭据。

该约束**只存在于界面**：服务端 `enqueueServerAutoMerge` 不校验任何 AI 前置条件，只校验步骤策略为 `autoMergePullRequest + executionMode='server'`、PR 号有效和重试上限。合并执行路径完全不调用模型。后续若要放开，只需去掉 `stageTimeline` 中 `mergeDisabled` 对 `autoDisabled` 的依赖，无需改服务端。

旧版浏览器端自动创建策略（`executionMode='browser-session'`）带不了服务端合并，该步骤的自动合并勾选框保持禁用，并提示用户先关闭再重新开启自动创建。

### 合并后门禁与下一步解锁（已实现，非本阶段新增）

「第一步合并后触发的 GitHub Actions 全绿，才算这一步彻底完成，才去判断第二步是否勾选自动创建」这条链已经生效，不属于待做项：

- `stageIsUnlocked` 要求前序步骤同时满足 `pull_state = 'merged'` 且 `checks_state = 'success'`，否则下一步保持 `locked`；
- 合并那一刻 `checks_state` 被重置为 `pending`，由合并后触发的 Actions 结果填成 `success` 或 `failure`；
- `mergeChecksWithDeployments` 把部署状态并入 `checks_state`：部署失败记 failure、部署进行中记 pending，因此配置了部署的步骤在部署未绿前不会解锁下一步。

第 6 阶段要补的是健康检查、多路径汇聚的完整推进与进度条展示，而不是这条基础门禁。

### 范围

本阶段只做自动合并。用户提出的「合并后 Checks/Actions 全绿再推进下一步」属于第 6 阶段，依赖合并后门禁、部署、健康检查与多路径汇聚，面大得多，应在自动合并跑通一轮后再接。

## 画布决策

第一阶段不需要画布。现有步骤编辑器足以表达当前需求，成本低、迁移风险小、用户认知连续。

只有在需要任意 DAG、条件分支、并行节点、汇聚节点、回滚路径或人工审批节点可视化时，才引入画布。画布应作为配置的另一种视图，不能成为唯一编辑入口，也不能改变服务端统一状态模型。

## 验收标准

- 默认关闭自动化时，现有手动流程行为完全不变。
- 同一标签页刷新后现有浏览器 AI Key 仍可用于手动流程；它不会被自动上传为服务端凭据。
- 服务端凭据的读取接口、日志、审计和数据库查询结果不暴露明文 Key；删除或解密失败会暂停自动运行。
- 自动创建 PR 只有在服务端自动流程凭据、AI 自动生成、自动确认和生成规则四项均满足时才允许用户开启；缺少任一项时开关不可用且有可操作提示。满足条件不会自动勾选，必须由用户主动开启。
- 单步骤开启自动合并时，只有该步骤可自动合并。
- 自动合并只使用 merge commit，且请求必须携带 `sha = pull.head.sha`；head 前进后这次合并必须失败而不是改合新 commit。
- `mergeable_state = 'behind'` 时暂停并给出可操作原因，不自动 update branch。
- 合并失败次数达到 `recoveryPolicy.maxRetries` 后停在 `paused`，不再被 stale 逻辑自动重排。
- 等门禁而留在 `queued` 的动作，在 `recoveryPolicy.cooldownSeconds`（随尝试次数翻倍、封顶 30 分钟）走完前不被排空重跑；而清门禁的事件到达后必须立即合并，不受该退避影响。
- 目标 PR 已是 merged 时记 `succeeded` 并带 PR 号，不调用合并接口、不产生失败记录。
- 自动合并策略可在未开启自动创建的步骤上单独存在：勾选后该步骤保存 `{ autoMergePullRequest: true, executionMode: 'server' }`，不带生成规则；关闭自动创建不会清除自动合并，反之亦然。
- 界面上自动合并的可勾选条件与自动创建一致：四项 AI 前置缺失时两个勾选框都为 `disabled`；服务端入队不校验这些前置。
- 自动合并勾选框位于流程详情页步骤卡片内「新提交数达到」输入框右侧的同一行；抽屉不提供自动化开关。
- Checks、Actions、审批、mergeability 任一未满足时不会执行合并；其中必需审批数须同时覆盖只写在 ruleset 里的审批要求。
- 合并后的所有配置门禁未全绿时不会创建下一步 PR。
- 多路径汇聚必须等待全部显式前置路径完成。
- 重复 Webhook、重复轮询和重复点击不会创建重复 PR 或重复合并。
- 暂停、失败、重试、恢复和最终结果均可在详情与审计中追溯。
- 运行中的策略修改不会改变已创建运行的快照。
