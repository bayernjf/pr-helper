## 一、代码质量评估

### 已做得好的地方

1. 核心规则有明确的事实来源：门禁判断在 [`src/lib/domain.ts`](../src/lib/domain.ts)，流程配置和排序在 [`src/lib/workflow.ts`](../src/lib/workflow.ts)，服务端同步和持久化在 [`api/_lib/workflows-store.ts`](../api/_lib/workflows-store.ts)。
2. GitHub App secret、OAuth secret 和 installation token 保持在服务端，浏览器没有直接持有生产级 GitHub 凭据。
3. 数据库变更使用有序 migration，没有在运行时执行 DDL，数据表之间也有外键约束。
4. Webhook 有签名校验和 delivery 去重，定时 reconciliation 可以补偿丢失或乱序事件。
5. 最近已经修复了多个真实生产级问题：流程编辑后的旧阶段状态、部署写入外键顺序、mergeability 未确认时误显示合并按钮、没有 Actions 时错误等待等。

### 主要工程问题

#### 1. 前端入口过于集中

`src/main.ts` 同时负责 DOM 渲染、页面状态、API 编排、抽屉、弹窗、GitHub 操作、AI 生成、草稿、通知和看板排序。当前规模尚可维护，但后续新增状态会放大回归范围。

建议逐步拆分为：

- 页面模块：overview、editor、detail、drawer。
- 服务模块：GitHub、workflow、notification、AI。
- 单独的前端状态容器和事件模型。

不建议一次性重写；应按功能边界逐步迁移，并保持每一步可回滚。

#### 2. 前端和服务端仍存在双状态来源

浏览器保留实时 GitHub `statuses`，服务端又持久化 `workflow_stage_states`、部署状态和待办队列。近期修复了多个显示不一致问题，但结构性风险仍在：不同页面可能组合不同来源得出结论。

目标应该是：服务端输出统一的阶段决策模型，前端只负责展示和触发操作；GitHub 原始数据作为详情，而不是由多个页面各自重新解释。

#### 3. 阶段索引仍广泛存在，稳定身份正在收敛

阶段状态主键仍依赖 `stage_index`，但流程数据现在会在浏览器加载、服务端保存和远端返回时补齐稳定 `stageId`，运行快照也会保存该 ID。用户拖动、删除或插入流程步骤时，旧状态表仍可能需要后续迁移到 `stage_id`，因此这项风险尚未完全关闭。

018 已完成 `stage_id` 回填和索引创建，但仍保留 `stage_index` 兼容。长期应新增 019，逐步切换主键、外键和核心查询；不要把“数组位置”继续当作业务实体身份。

#### 4. 缺少浏览器 E2E 测试

当前测试主要是纯函数和服务端单元测试，不能覆盖之前反复出现的真实 UI 问题，例如新建/编辑页面、抽屉同步、菜单关闭、拖拽排序、语言切换和授权返回。

建议至少覆盖一条完整浏览器链路：

```text
登录 → 选择仓库 → 新建流程 → 配置步骤 → 创建 PR → 刷新状态 → 打开抽屉 → 合并/失败处理
```

## 二、功能质量评估

### 已经形成的真实闭环

- 多项目 Lane 看板，以及 Lane 和流程步骤排序。
- 线性流程、动态分支规则、独立合并路径和多路径汇聚。
- 创建 PR、读取 Checks/Commit Status/Review/分支保护/mergeability。
- 没有 Actions 时不无限等待；Actions 未完成或 GitHub mergeability 未确认时不显示可合并状态。
- PR 合并后追踪 Actions、Vercel/Cloudflare Preview 和 Production 部署。
- 部署失败重试、失败摘要、Codex 修复上下文和确认式 Production 回滚。
- GitHub Webhook、定时校准和 Web Push 通知。
- AI 流式生成 PR 标题和描述，24 小时草稿恢复，Markdown 生成规则管理。
- GitHub App 授权仓库管理和用户级流程持久化。

### 仍然存在的功能风险

#### 1. 缺少完整的“流程运行”实体

当前主要保存“每个步骤当前是什么状态”，还没有完整保存某一次发布运行的配置快照和生命周期。因此还不够好地回答：

- 这是第几次发布？
- 这个 PR 属于哪一次发布？
- 流程修改前后的运行配置有什么不同？
- 这次发布失败和上一次失败是否是同一原因？

#### 2. 状态新鲜度不够显式

用户能看到状态，但不一定知道状态是刚由 Webhook 更新、由 cron 更新，还是已经过期的缓存。状态停住时，用户容易把“没有变化”误解为“系统没有问题”。

#### 3. 关键动作审计还不够团队化

创建 PR、合并、Actions 重试和回滚应该完整记录操作人、时间、操作前状态、GitHub 返回结果和失败原因。目前已有事件记录基础，但还不是完整审计系统。

#### 4. 并发和异常边界需要专项回归

建议真实验证以下场景：

- 同一 Source → Target 同时存在多个 PR。
- PR 被关闭后重新打开。
- PR 被 force-push 或发生冲突。
- Review 被 dismiss，Required Check 被改名。
- Actions 被取消、重跑或长时间无结果。
- Webhook 重复、延迟、乱序，或 GitHub API 限流。
- App 授权仓库权限被撤销。
- 分支删除、环境保护规则改变。

## 三、产品完善度评估

产品定位是成立的：GitHub 是代码和门禁事实来源，Codex/Claude 是工程执行者，PR Helper 是跨项目发布流程的控制台。

目前产品更接近“个人或小团队发布工作台”，距离团队级控制塔还缺少：

- 用户、团队、角色和项目权限。
- 流程版本及运行快照。
- 完整发布历史和耗时分析。
- 失败处理中心。
- 同步健康度和数据新鲜度。
- 流程预检。
- 通知订阅中心。
- 审计、保留策略和数据导出。

## 四、最值得投入的新增功能

### P0：可控的 PR 流程自动化

用户已经明确需要在门禁通过后自动合并 PR，并在合并后的 Checks、Actions、部署和健康检查全部成功后自动推进下一步。建议先实现无画布的逐步骤自动化策略，避免引入新的流程图编辑复杂度：

- 新提交触发阈值。
- 自动创建 PR、自动合并和合并后自动推进开关。
- 自动创建 PR 的硬性前置校验：AI 设置必须同时开启自动生成标题/描述与自动确认创建，并且至少存在一条有效 Markdown 生成规则；缺少任一项时开关不可启用。三项满足只代表允许用户开启，不得自动勾选。
- 每一步独立策略，默认关闭高风险动作。
- 服务端策略快照、动作幂等、暂停/恢复、超时和失败升级。
- 自动合并严格复用 GitHub 原生门禁与统一阶段决策。
- AI 失败处理第一版只生成修复上下文或 Codex 修复任务。

详细设计、数据模型方向和验收标准见 [`docs/automated-workflow-plan.md`](automated-workflow-plan.md)。

### P0：统一状态模型与同步健康度

这是当前最高价值投入，优先级高于模板、复杂 DAG 和更多视觉功能。

建议实现：

- 每个项目显示最后成功同步时间。
- 显示 Webhook、cron、手动同步的最近状态。
- 标记数据是否过期，并显示最近失败原因。
- 标记每个步骤的数据来源和时间。
- 提供“强制重新校准”。
- 服务端记录 reconciliation 耗时、失败率和处理数量。
- 所有页面使用同一套服务端阶段决策。

验收标准：用户可以明确知道某个状态“是什么、来自哪里、更新时间、是否可信”。

### P1：流程版本与运行快照

每次保存流程生成版本；每次启动一次发布运行时保存完整快照。流程修改只影响新运行，历史运行永远保留当时的 Source、Target、依赖、门禁和部署配置。

验收标准：修改流程或拖动步骤后，已经开始的运行展示不变，新运行使用新版本。

### P1：发布历史时间线

把创建 PR、检查、审批、合并、部署、健康检查和回滚串成一条可检索时间线，并记录各阶段耗时、失败次数和操作人。

验收标准：用户可以从一个发布运行还原完整经过，不需要打开多个 GitHub 页面拼接信息。

### P1：失败处理中心

集中展示 Actions 失败、审批不足、冲突、部署失败、健康检查失败和同步失败，并提供日志、重试、Codex 修复上下文、重试次数、冷却时间和人工升级。

### P1：团队权限与审计

至少区分 Owner、Editor、Operator、Viewer，并将 Production 合并和回滚设为独立权限。所有高风险操作保留不可变审计记录。

### P2：流程预检

在创建 PR 前检查分支、重复 PR、冲突、上游依赖、App 权限、Actions、Environment 和分支保护，提前给出可执行的修复建议。

### P2：通知订阅中心

在 Web Push 之外，支持按项目、失败类型、审批责任和 Production 事件订阅，并预留 Email、Slack、飞书和企业微信。

### P3：发布分析

在运行历史稳定后增加平均发布耗时、Actions 耗时、部署成功率、回滚次数、失败率和最常阻塞门禁等指标。

## 五、容易被忽略的高价值问题

### 安全

[`api/github/[action].ts`](../api/github/[action].ts) 已增加路径/方法白名单，高风险 Actions 重试也已移到服务端校验。后续仍需补充 CSRF 防护、速率限制和更完整的操作审计。

### 数据隐私与恢复

PR 草稿和生成规则目前只在浏览器 `localStorage` 中保存，换设备不会同步，清除浏览器数据会丢失。云同步前需要先设计加密、密钥管理、租户隔离和数据保留期限。

### 成本和配额

GitHub API、Actions、Vercel、Cloudflare、Webhook 和 Push 都有配额或失败边界。应记录 API 限流、cron 延迟、Actions 超时和通知失败，避免系统在配额耗尽时只显示“状态未知”。

### 可访问性和国际化

需要继续验收键盘操作、焦点管理、`aria` 状态、窄屏布局、长仓库名/分支名和中英文文案一致性。当前产品有国际化基础，但布局回归仍值得用浏览器测试锁定。

## 六、暂不建议优先投入

当前不建议优先开发：

- 流程模板市场。
- 任意 DAG 编辑器和复杂条件分支。
- 自动修改代码。
- 自动 Production 合并或自动回滚。
- 自建完整 CI/CD 执行引擎。
- 大量第三方平台接入。
- 纯视觉装饰性优化。

这些功能会扩大复杂度，但不能解决当前最核心的状态可信度和团队安全问题。

## 七、非验收类后续开发

以下事项不依赖当前 Preview 验收结果之外的额外数据库操作，按可靠性和风险排序：

1. **稳定阶段身份正式切换**：019 已将状态、事件、部署和运行记录的核心查询从 `stage_index` 切换到 `stage_id`；下一步完成 Preview 回归。
2. **并发与幂等保护**：流程版本保存增加并发控制；创建 PR、合并、Actions 重试和回滚增加幂等键；API 增加 CSRF 防护和限流。
3. **统一服务端状态模型**：由服务端输出阶段决策，前端只展示和触发操作，减少不同页面分别解释 GitHub 状态造成的不一致。
4. **完整操作审计**：记录操作人、时间、前后状态、GitHub 返回结果和失败原因，并支持查询和导出。
5. **浏览器 E2E 测试**：覆盖新建/编辑流程、步骤排序、抽屉、授权返回、创建 PR 和失败恢复等高风险路径。
6. **加密云同步加固**：补充密钥轮换、设备恢复、多设备冲突处理和数据保留策略。
7. **历史数据保留与清理**：为事件、部署、运行、Webhook delivery 和审计日志定义保留周期及清理任务。
8. **团队权限模型**：增加团队、角色、项目和流程级权限。

当前不建议优先投入流程模板市场、任意 DAG 编辑器、自动生产合并/回滚或自建 CI/CD 执行引擎。这些功能会扩大复杂度，但不能先解决状态可信度和操作安全问题。
