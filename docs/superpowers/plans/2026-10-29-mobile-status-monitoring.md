# 移动端实时状态监控需求（2026-10-29）

> 状态：需求记录（尚未实施）。本文记录使用者的真实使用场景与已确认的需求方向，作为后续排期依据，不替代实施方案。

## 一、背景：使用场景

使用者目前通过**移动端豆包远程控制桌面端豆包**工作：手机是唯一的操作与反馈通道，桌面端豆包在被控电脑上执行实际命令（git / gh / 部署等）。

在远程控制场景下，桌面端的 pr-helper 看板无法被直接查看，导致三个实时性缺口：

1. **每个产品的 git 状态**看不到（分支领先/落后、工作区状态、最近提交）；
2. **PR 状态**看不到（打开/待合/已合并、门禁是否全绿）；
3. **CI 失败**无法实时感知（失败了不能第一时间知道并处理）。

涉及范围：使用者维护的多个产品仓库（Agent 项目矩阵，具体清单待使用者点名）。

## 二、已确认的结论

- **移动端不是锦上添花，是本场景的刚需**——手机是被控工作流下唯一的反馈通道。
- **不需要原生 App / 完整移动端改造**：单人工具，App 与全面响应式改造性价比低。
- 需求按三层拆解，①② 覆盖约 90% 场景，③ 为可选增强：

### ① 被动实时通知（最高价值，优先实施）

CI 失败 / 流程暂停 / 需要处理时主动推送到手机，无需使用者主动查看。

- 主推载体：**飞书机器人 webhook**（使用者已在飞书生态内）。
- 触发点：
  - GitHub Actions 失败时（workflow 加 `if: failure()` 步骤）；
  - pr-helper 对账发现 `paused` / `failure` 时推送。
- 备选通道：Server酱 / PushDeer / Bark 等纯手机推送。
- 不做任何前端改动即可落地。

### ② 主动按需查询（零成本，立即可用）

手机豆包直接下指令（如"汇总 XX 仓库的 git 状态 / PR / CI"），桌面端执行 `gh` 聚合脚本回传结果——远程控制链路本身就是移动端入口。

- 交付物：一条聚合脚本，遍历产品仓库清单，输出每个仓库的 PR 数、CI 红绿、分支领先/落后状态表。
- 脚本存于桌面端，随时可被远程调用。

### ③ 统一状态页（可选增强，后置）

极简响应式页面：一屏列出所有产品仓库的 PR / CI / 分支状态，手机浏览器打开自动刷新。价值是"扫一眼"，工作量中等。

## 三、待使用者确认的输入

1. "每个产品"具体是哪些仓库（仓库清单）；
2. 推送通道选飞书还是纯手机推送；
3. ①② 的实施顺序（建议先做 ①）。
